# CTI Product Assistant — Spec

What the application is and what its parts are contracted to do. This is a
contract, not a sequence — see `docs/week14/plan.md` for build order.

---

## Product

A public RAG chat application answering product and price questions over the
CTI price masterlist: 1,038 items of workplace safety, facility and
institutional equipment.

**User.** A sales staffer, dealer, or prospective customer asking "how much is
X", "what do you have under ₱Y", "what do I need for a construction site".

**Non-goal.** Not an ordering system, not an inventory system. It quotes list
prices and explains the catalog. Stock, lead time, discounts and delivery are
explicitly out of scope and must be refused, not estimated.

## Data

Source of truth is `corpus/`, generated by `scripts/build_corpus.py` from
`fixed-cti-masterlist.xlsx`. See `corpus/README.md` for record shape and
`docs/corpus-design-decisions.md` for why it is shaped that way.

**Storage — two mechanisms, deliberately:**

- **Upstash Vector** holds the vector index over the `text` field of each
  product chunk, plus the guide documents chunked by `##` heading. Hosted,
  serverless REST — no connection pooling inside a Vercel function, and the
  index survives restarts.
- **An in-memory array** backs `filterProducts` **and the exact-match half of
  hybrid search**. `products.json` is imported at module scope and filtered
  with plain JavaScript — no database call. The corpus is ~1 MB, static, and
  regenerated by a build script, so counts, sorts and range filters are exact
  and instant without query-language friction.

**Hybrid retrieval needs no keyword index.** Exact `code` and `name` matching
runs as a regex/string scan over the same in-memory array — 1,038 records is
instant. This removes the dependency on the vector store's full-text
capabilities entirely, which is why the store choice is free.

Chunks are atomic — one product each — and must not be re-chunked at ingest.

**Decided M3 (2026-09-22): identical duplicates collapse, conflicting ones do
not.** Eleven codes appear twice in the masterlist with the same name and price
(flagged `duplicate_code_identical`, 22 records — see
`docs/data-quality-report.md` §2). Both tools collapse these to a single item:
`searchProducts` returns the product once, and `filterProducts` counts it once
in `total_matching`. The catalog therefore holds **1,027 distinct products**
across 1,038 records, and `total_matching` is a count of products, not of rows.

The five codes flagged `duplicate_code_conflict` are **never** collapsed — the
rows disagree on price, and both must reach the model for system-prompt rule 5
to fire.

De-duplication happens in the tool layer, not at ingest: every record is still
embedded and stored independently, because a record is a real row and the seed
must stay a faithful mirror of the corpus.

**Metadata carried on every product chunk:** `id`, `code`, `code_group`, `name`,
`category`, `department`, `price_php` (integer), `price_band`, `currency`,
`colors`, `attributes`, `source_row`, and `data_quality_flag` where present.

Guide chunks carry `doc_type: "guide"`, `title`, and the section heading.

## Tools

The capstone has nine tools, defined in `lib/tools.ts` and built per request
by `createTools({ sessionId })`. The two retrieval tools below keep their
Week 14 contract. The capstone adds `getProductDetails`, `compareProducts`,
`lookupApplianceWattage`, `recommendPowerStation`, `showApplianceChecklist`
(client-side), `buildQuotation` and `escalateToSales` (`docs/plan.md`, M2 to
M4). Tool descriptions must make the boundary unambiguous — vague
descriptions are a named failure mode in the brief.

**Errors (M5).** Every tool body runs inside `safeExecute`. A failure returns
`{ error: "tool_failed", message }` and never throws into the stream. When the
vector store fails, `searchProducts` returns
`{ degraded: true, message, items }` with exact code and name matches only.
`SIMULATE_VECTOR_FAILURE=1` forces that path for tests.

### `searchProducts`

Semantic and keyword search over product chunks and guide documents.

```ts
searchProducts({
  query: string,              // natural language or product code
  department?: string,        // optional narrowing
  limit?: number              // default 12, max 20
}) => Array<{
  code, name, category, department,
  price_php, price_band, colors, attributes,
  text, score, data_quality_flag?
}>
```

**Use for:** naming or describing a product, asking what something costs,
asking whether an item is carried, and any conceptual question about the
catalog, codes, or pricelist conventions.

**Behaviour.** Exact matches on `code` and `name` — found by scanning the
in-memory array, not by a second store query — are merged ahead of vector hits.
A query that looks like a product code (`/^[A-Z]{3}-\d{3}/i`) must return its
exact match first when one exists.

### `filterProducts`

Direct query against the in-memory product array. Not semantic, no database
call.

```ts
filterProducts({
  category?: string,
  department?: string,
  min_price?: number,
  max_price?: number,
  color?: string,
  oshc_only?: boolean,
  sort?: "price_asc" | "price_desc" | "name",
  limit?: number              // default 20, max 50
}) => {
  items: Array<{ code, name, category, price_php, ... }>,
  total_matching: number      // before limit — required for count answers
}
```

**Use for:** price thresholds ("under ₱500"), superlatives ("cheapest safety
shoe"), counts ("how many chairs"), and browsing a category.

**Why separate.** Vector search answers these confidently and wrongly — asked
for everything under ₱500 it returns `limit` arbitrary rows and presents them
as complete. `total_matching` exists so the model can say "23 items match,
here are the 20 cheapest" rather than implying it has listed them all.

## Retrieval configuration

| Parameter | Value | Rationale |
|---|---|---|
| topK | 12 (max 20) | Chunks are short and single-product; variant families need to return together |
| Chunk strategy | One product per chunk, no overlap | Overlap is meaningless for atomic records |
| Guide chunking | By `##` heading | Each chunk is a self-contained explanation |
| Hybrid merge | Exact code/name matches first, then vector by score | Codes are near-identical under embedding |

Tunable during M3. Any change made for a reason should be recorded in
`docs/corpus-design-decisions.md`, since retrieval tuning is reflection
material.

## System prompt contract

The model must follow these rules. Each number is the same rule in
`lib/prompt.ts` (prompt V1, M5). Change both together.

1. Quote prices **only** from tool results. Never estimate, interpolate, or
   recall a price from general knowledge.
2. State the **product code** alongside every price.
3. Format prices as `₱43,470.00`, with thousands separators.
4. When several variants exist (sizes, capacities, chemical types), **list every
   one with its own price**. Never let one item stand in for another of the
   same size.
5. When a tool result carries `data_quality_flag: "duplicate_code_conflict"`,
   **warn** that the masterlist holds conflicting entries for that code and
   refer the user to the sales team. Do not pick a price.
6. When tool results do not clearly match the question, **say so and ask for
   the product code** rather than answering from the closest match.
7. **Refuse and redirect** on stock availability, lead time, discounts,
   delivery cost, warranty, after-sales service, supplier, and quality
   comparisons. Look the item up first, then give the code and price. For
   commercial terms, call `escalateToSales` with reason `commercial_terms`.
8. Mention **related items** only where a retrieved guide section documents a
   buying pattern.
9. **Specs, usage, advantages and cautions** come only from a knowledge sheet:
   `getProductDetails`, `compareProducts`, or a sheet section that
   `searchProducts` returns. Status `not_on_file` gives "not on file", the code
   and the price, and an offer to escalate. This replaces the Week 14 rule
   that refused all specs beyond the item name.
10. **Compare** 2 to 4 products with one `compareProducts` call. Write "choose
    A if…, choose B if…" from the rows only. A `null` value is "not on file".
    A quality question is still a refusal under rule 7.
11. **Power-station sizing.** Code does all the arithmetic. No appliances named:
    show the checklist. Appliances named: one `lookupApplianceWattage` call per
    appliance, then one `recommendPowerStation` call. Use the `suggested`
    variant and say which one. Never calculate watts, watt-hours or runtime in
    text. A life-critical device escalates with reason `life_critical`.
12. **Quotations** come only from one `buildQuotation` call. Never add prices,
    compute VAT or write a total in text. A bulk flag escalates with reason
    `bulk_order`. After a quotation, the text is at most two sentences.
13. **Escalation.** Call `escalateToSales` once for a trigger in its
    description. Never ask for personal details in chat. The contact form
    collects them.
14. **Session memory.** A "Session memory" system message can give a summary,
    the saved quote list and the last recommendation. It holds codes and
    quantities only. "Add it to a quote" means the first eligible code of the
    last recommendation. A change to the quote list sends every line again in
    one `buildQuotation` call.
15. **Tool failures.** A `degraded: true` search result is reported to the
    customer. A `tool_failed` error is reported as a failed lookup, with an
    offer to retry or escalate. The model never fills the gap itself.
16. **Safety claims (M7).** No claim that an item is certified, approved,
    rated or compliant for a use unless a sheet in this turn's tool results
    says so. The answer guard (`lib/guardrails/answer-guard.ts`) enforces
    "certified" and "approved for" in code: a draft with either word and no
    tool result that holds it is rewritten once, then replaced with the
    sales fallback.

### Runtime guardrails (M7)

The route checks input and output in code, not only in the prompt:

- Every user message is PII-masked (`[PHONE]`, `[EMAIL]`, `[TIN]`, `[CARD]`)
  before the model call and before the log.
- The latest user message goes through `checkInput`. Injection and unsafe
  content get a fixed refusal. Off-topic gets a fixed redirect. No chat-model
  call runs for either.
- The text of each step is held until the step ends. Every ₱ figure, product
  code and watt figure must appear in a tool result, the session memory or a
  user message of the chat. The digits inside a product code do not count as
  figures.
- One JSON log line per request: `lib/log.ts`.

### Two cross-cutting constraints added in M4

Added after the first graded run, and binding on the prompt alongside the
numbered rules above.

**A. Nothing in the prompt is a source of fact.** The model may not state a
product code, price, or product name that did not appear in a tool result in
the current turn — including one that appears in its own instructions. The
first prompt illustrated a refusal with a made-up price and the model quoted
that price to the customer (see `docs/week14/plan.md`, M4). Prompt examples now
demonstrate format only.

**B. A tool call is required before a refusal.** Refusing a question about
stock, discounts or warranty is still answering a question about a real
product. The lookup happens first; the answer then refuses the uncovered part
and quotes the code and price that were retrieved. Skipping the call is the
condition under which invention occurred.

**C. Filters are never narrowed beyond what was asked.** If the question does
not name a real department or category, `filterProducts` is called on price
alone. A guessed filter returns a complete, correct list for a question the
customer did not ask, and `total_matching` cannot reveal the substitution —
"4 items" where the true answer is 214.

### Answer format — decided 2026-09-22, after seeing M3's raw output

A multi-item answer renders as a **compact table**: code, the distinguishing
attribute (size, capacity, colour), price. One sentence of context above it,
one below. A single-item answer stays a sentence.

```
CTI carries two fire blanket lines.

| Code | Size | Price |
|---|---|---|
| FIR-001-11A | 1.0×1.0 | ₱650.00 |
| FIR-001-11B | 1.2×1.2 | ₱830.00 |
| FIR-002-A | 1.2×1.2 | ₱1,050.00 |

The FIR-002 line is priced higher across every size.
```

**Why.** The placeholder prompt produced numbered lists with every field
bolded, which reads as shouting and makes a twenty-item price answer
unscannable. A table lines the prices up so they can be compared, which is the
actual job.

**Banned phrasings.** No "you can order any of these by quoting the product
code" — this application quotes list prices and does not take orders (see
Non-goal). No bolding of whole lines.

*Consequence for M5:* a wide table must sit in its own horizontally scrolling
container at 375px, or it breaks the mobile layout.

## Interface

**Chat.** Streaming responses (R2). Tool calls visible while running, so the
user sees retrieval happening rather than a dead pause.

**Sources render as soon as retrieval completes, not when the answer does.** A
tool-calling turn runs tools first and generates text second, so the full
source set is known before the first token arrives. The panel populates at that
point and the answer streams in beside it — the user sees what is being
grounded on before reading the claim. Do not defer source rendering to message
completion; it discards information that is already available.

**Citations are panel-only. No inline `[1]` markers.** The brief requires
showing retrieved sources, not inline reference markers. Getting a model to
emit markers reliably is prompt-tuning effort with no rubric payoff, and the
source cards — code, name, category, price — already make the grounding
visible. Revisit only if M5 finishes early.

The starter satisfies this already: `useChat` exposes `toolInvocations`, and an
invocation reaches `state === 'result'` before the text part begins streaming.
Render sources off that state rather than off message completion.

Deferred to M5: how sources group when a turn calls both tools, and the
stop/abort control.

**Sources panel.** Every answer that used retrieval shows its sources as
product cards: code, name, category, price, colors. The displayed price renders
from the `price_php` metadata field — **never** parsed from model output. This
is what makes the shown number exact by construction.

Guide-document sources render differently from product sources: title and
section heading rather than a product card.

**Empty state (R6).** Not a blank box. States what the assistant covers, and
offers suggested-prompt chips drawn from the real catalog — one per question
type:

- "How much is MED-001-01?"
- "What fire extinguisher types do you carry in 10 lbs?"
- "What safety equipment do you have under ₱500?"
- "What do I need to outfit a construction site?"

**Mobile.** Usable at 375px. Sources panel collapses below the chat rather than
sitting beside it.

## Security

- All API keys server-side only, in route handlers. No key reaches the client
  bundle (R5).
- Env vars: named identically in `.env.local` and in Vercel project settings.
  Mismatched production env var names are a named failure mode in the brief.
- `.env.local` gitignored. Verified before first push.
- Session memory (M5): the `cti_sid` cookie (random UUID, httpOnly,
  SameSite=Lax, 7 days) keys `session:<id>` in Redis, TTL 7 days. It holds
  codes, quantities, loads and a summary. No personal data.
- Contact details reach Redis only through the contact form, with consent
  (M4). They never pass through the model.

---

## Out of scope

Authentication, ordering, image display, admin editing of the corpus. The
capstone brings draft quotations (M4), session memory (M5) and rate limiting
(M8) into scope. The chat history itself is not restored after a reload. Only
the saved quote list is.

Stretch goals are capped at two by the brief. Committed: **hybrid retrieval**
(required by the corpus shape, already specified above) and **suggested-prompt
chips** (doubles as the empty state). Anything else is out.
